## Options

### O1 — Agent prompt wiring: inline vs file-based (real fork)

The two SDD agent styles already coexist:

- **A. Inline prompts** (used by `sdd-architecture-lint`, `sdd-changelog`): the whole executor prompt is a JSON string in `opencode.sdd.json`. Pros: zero sync changes (nothing added to `OWN_PROMPTS`); self-contained. Cons: duplicates the language-contract boilerplate in every agent; hard to version/review inline in JSON; the launch prompt is large if the 4 council agents each carry full lens definitions.
- **B. File-based prompts** (used by `sdd-rfc-author`): `prompt: "{file:./prompts/sdd/sdd-<name>.md}"`. Pros: clean, versionable docs; single source consistent with the skill; matches the `sdd-rfc-author.md` precedent. Cons: each new file must be added to `OWN_PROMPTS` (line 105) to be synced to `~/.config/sdd-own/prompts/sdd/` + symlinked into `opencode`/`claude` prompt dirs; more sync surface to keep green (T30).

**Recommendation: B (file-based) for `sdd-council` (the orchestrator-of-lenses prompt is substantial and includes the acta format/flows), and B or A for the 3 lens agents.** Concretely: reuse the `sdd-rfc-author.md` pattern — a single `sdd-council.md` prompt file is warranted because it encodes the council orchestration contract (parallel `task()` to 3 lenses, consolidation, convergence/fork/frame logic, acta persistence). The 3 lens agent prompts are small ("review `design.md` through lens X, return verdict") and can be **inline** (mirroring `sdd-architecture-lint`/`sdd-changelog`), OR one shared file-prompt if lens wording must be identical. **Preferred: `sdd-council` uses file-based `sdd-council.md`; the 3 lens agents use inline prompts** (minimal sync surface, reusing the existing inline precedent, keeping the two existing styles). If the user prefers uniform file-based for all 4, add 4 files to `OWN_PROMPTS`.

### O2 — Council lenses: one skill vs per-lens skills (real fork)

- **A. Single `sdd-council` skill** with a "Lens definitions" section defining arch/product/risk internally; the 3 lens agent prompts reference that skill. Pros: one full-install skill (matches exclusive-skill pattern), less sync surface, single source for lens framing. Cons: the lens agents and the council share one file; re-framing (fresh voices per round) is purely prompt-level, not file-level.
- **B. Per-lens skills** (`skills/sdd-council-arch/`, `-product/`, `-risk/`), each a full-install exclusive skill. Pros: maximal independence (each agent loads its own SKILL.md, true "fresh voices"); auto-discovered by sync with no script change. Cons: 3 more skills to maintain; heavier footprint; the RFC only borrows the *lens concept*, not necessarily separate skills.

**Recommendation: A (single `sdd-council` skill)**, with the 3 lens **sections** inside it, and the 3 lens agents' prompts pointing at the same skill (each to its lens section). This matches the RFC wording ("each with a dedicated lens skill **or lens section inside `sdd-council`**", Goal 2) and the user's own Anti-Goal 4 note that only the lens categorization is borrowed. 3 separate full-install skills is over-engineering unless arch-lint reverse evidence demands per-lens versioning.

### O3 — `sdd-council` agent: single orchestrator-of-lenses vs the 3 lenses called directly by the orchestrator (real fork)

- **A. `sdd-council` agent orchestrates the 3 lens agents internally** (council calls `task()` to lens agents, consolidates, persists acta, returns convergence/fork verdict to the orchestrator). Matches the RFC's flow diagram (lines 77-92): "sdd-council → orchestrates 3 lens agents in parallel via task()". **This is what the RFC specifies.**
- **B. The orchestrator calls each of the 3 lens agents directly** and runs the consolidation inline. Violates the RFC flow and would bloat orchestration context (against the `no-git-crudo`/delegation rules). Rejected by the RFC.

**Recommendation: A.** Note this requires the **generous-council** agent (`sdd-council`) to itself have `task` permission to spawn the 3 lens agents — i.e. `sdd-council` must be a `mode: primary`-or-`mode: subagent`-with-task who can `task()` the lens agents. Check: the lens agents' calls come from `sdd-council`, not from the orchestrator. So the orchestrator `task` allow-list needs `sdd-council`, and **`sdd-council` itself needs a `task` allow-list** for the 3 lens agents. This is a real wiring point to nail in the proposal.

### O4 — Orchestrator hook placement (minor, mostly resolved)

RFC says hooks land in (a) Organic Support Phase Hooks, (b) command overlay SUPPORT-CONDITIONAL, (c) the skill. Evidence: orchestrator rule 4 (line 493) **+** Organic hooks item 3 (arch-lint) are the two contract homes; `sdd-continue.md` SUPPORT-CONDITIONAL and `sdd-ff.md` item 6 are the command-overlay homes. **Recommendation**: update all four (rule 4, organic-hooks item 3, sdd-continue SUPPORT-CONDITIONAL, sdd-ff item 6); consider whether `sdd-new.md` needs the council trigger (it currently has none).

## Risks

1. **gentle-ai v2.x managed-agents constraint.** The 4R agents remain untouched; the RFC already established they're unusable (`GENTLE_AI_REVIEW_BINDING`, `permission: {"*": "deny"}`, hidden, RDD-only). Risk is only if the proposal tries to *wrap* them — the RFC's Anti-Goal 4 forbids it. Keep the council agents strictly ORG-OWNED (no `__managed_by`), else sync/merge may treat them as Alan's.
2. **Orchestrator `task` allow-list + `sdd-council`'s own `task` permission.** If `sdd-council` (the lens orchestrator) lacks `task` access to the 3 lens agents, the whole parallel flow breaks at runtime. This is a **permission-wiring risk** that the RED checks must pin (e.g. assert `sdd-council` has `task` allow for the 3 lens names, and `gentle-orchestrator` can `task` `sdd-council`).
3. **T30 zero-desync hazard (stale-pin class).** T30 asserts `./sync-skills.sh --check` prints zero `[DESYNC]` and errors 0. If the new skill/agents/prompt-files are added without the corresponding sync deployment (e.g. a file-based prompt file not added to `OWN_PROMPTS`, or a skill dir not symlink-correct), T30 fails. Any change to `OWN_PROMPTS` (for file-based agents) or to `skills/` is the exact T30/T29-class stale-pin surface.
4. **T31 pin interference.** T31 (F4 hook pins) greps `orchestrator.md` for specific strings (`gentle-ai review status`, `review-integration/v2`, `next-transition`, `consent/v3`, `never skips human authorization`, `candidate-scoped`, `continues to archive`, `informational no-op`). Editing rule 4/Organic hooks must NOT remove these strings (they live in the F4 post-verify hook, lines 405-414, and consent block). Guard: keep F4 text byte-stable.
5. **Arch-lint `N/A`-skip removal is a behavioral change.** Existing `sdd-ff.md:9` and `sdd-continue.md` SUPPORT-CONDITIONAL describe the old boundary-conditional skip. Updating them is required; if inconsistently updated, an entry route could still skip arch-lint on a boundary-free change — regressing the RFC's "arch-lint ALWAYS fires" invariant. Any red check asserting the old skip must be removed.
6. **`openspec/changes/{change-name}/council.md` + Engram mirror drive-by.** The acta is written by `sdd-council` at two homes (file + Engram topic `sdd/{change-name}/council`). Error-handling (agent partial write in one store) could orphan a half-persisted acta, which arch-lint axis 2 would then fail-closed on (safe direction — fail-closed is the design, but a false negative blocks the chain). The proposal should spec a single writer for the acta and an idempotent write.
7. **`sdd-council` statelessness across rounds.** RFC Operational note (line 149): retry budget is tracked by orchestrator state, not by the skill. If `sdd-council` (or the lens agents) attempt to carry round-1 state into round 2, convergence/fork could be corrupted. Risk mitigated by keeping the skill stateless and the orchestration/round logic in the orchestrator flow control.
